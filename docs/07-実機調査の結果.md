# 07. 実機調査の結果 — SC-06D 実機から判明したこと

**このドキュメントだけは実機の出力に基づいています。** 他のドキュメントは
公開ソースの読解が根拠ですが、ここは実際の SC-06D から取れた事実です。

- 端末: SC-06D / `d2dcm`
- ROM: **Android 4.0.4**、`samsung/d2om/d2dcm:4.0.4/IMM76D/SC06DOMAMA2:user/release-keys`
- 取得方法: `tools/oneseg-probe.sh` + `tools/analyze-oneseg-blobs.py`
- スキャンした ELF: **788 個**

---

## 1. 結論を先に

**ワンセグ移植の見通しは、事前の想定よりかなり良いです。**

理由は 1 つです。**`/dev/isdbt` を開いているライブラリが 1 つだけで、
しかもその依存関係が異常に軽い**ことが分かりました。

```
libonesegdmxdriver.so          ← /dev/isdbt を開くのはこれだけ
    ├── libonesegutils.so
    │       └── libPGL.so
    └── liblog / libcutils / libutils / libc / libstdc++ / libm  (AOSP)
```

**移植すべき独自ライブラリは 3 つだけ**です。そして重要なのは、
このチェーンが **`libbinder.so` も `libandroid_runtime.so` も
`libsurfaceflinger_client.so` も要求していない**ことです。

さらに、**録画を「TS をそのまま書く」方式にする**と決めたので
（3.3 節）、CPRM とその周辺も移植対象から外れました。
**純正から持ち込むのは、この 3 ファイルで全部です。**

この 3 つは Jelly Bean 時代の blob を Android 9 で動かすときに
最も詰まる相手で、特に `libsurfaceflinger_client.so` は
**Android 9 には存在すらしません**。それを避けて通れる、というのが今回の最大の収穫です。

## 2. カーネル側 — 想定通り動いている

```
OK   char major 225 registered: 225 isdbt
OK   /dev/isdbt: crw-rw-rw- system system 225, 0
```

`docs/06-調査ログ.md` でソースから読み取った内容（char major 225、
`register_chrdev` + `class_create` + `device_create`）が、実機で裏付けられました。

### パーミッションは `system:system 0666`

**当初この値を `media:media 0660` と想定していましたが、間違いでした。**
実機は **owner/group が `system`、モードが 0666**（誰でも読み書き可）です。

`device/samsung/d2dcm/rootdir/etc/init.oneseg.rc` を実機の値に修正済みです。
ここを締めると純正ライブラリが EACCES で転ぶので、**まず 0666 で動かしてから
締める**のが正しい順序です。

### dmesg は空振り

```
WARN no isdbt/nmi326 lines in dmesg
```

リングバッファが一周しただけです。**ワンセグアプリを起動してから再実行**すれば
`>ISDBT<` のログが取れます（`CONFIG_ISDBT_NMI_DEBUG=y` 相当が純正でも有効なら）。

## 3. ユーザー空間 — スタックの全体像

Samsung / NTT 系の「SDtv」スタックでした。

### 3.1 ティア 1: チューナに触る最小構成 ★

| ファイル | 役割 |
|---|---|
| `lib/libonesegdmxdriver.so` | **`/dev/isdbt` を開く唯一のライブラリ** |
| `lib/libonesegutils.so` | 共通ユーティリティ |
| `lib/libPGL.so` | その下請け |

`libonesegdmxdriver.so` の `DT_NEEDED`:

```
libonesegutils.so, liblog.so, libcutils.so, libutils.so,
libc.so, libstdc++.so, libm.so
```

AOSP 側で気にすべきは実質 **`libutils.so` だけ**です（C++ ABI が JB と Pie で違う）。
`liblog` / `libcutils` は C API で比較的安定、`libc` / `libm` は問題なし。
`libstdc++.so` は Android 9 にも存在するはずですが、**要確認**です。

`libutils.so` で詰まった場合の対処は、d2att-unified がすでに持っている
`libsamsung_symbols`（互換シンボル層）を拡張することです。

### 3.2 ティア 2: 純正の TS デマルチプレクサ — **不要と決定**

| ファイル | 役割 |
|---|---|
| `lib/libonesegdemux.so` | TS 分離 |
| `lib/libsdtvphmem.so` | 共有メモリ |
| `lib/libsdtvcrypto.so` | 暗号処理 |
| `lib/libonesegcprmapi.so` | CPRM（録画保護）。`/efs/` を読む |
| `lib/libBroadcastProcObs.so` | プロセス監視 |
| `bin/OneSegTsDemux` / `bin/broadcastProcessObserver` | デーモン |

**このティアは丸ごと移植しません。** `libonesegdemux.so` は
`libbinder.so` と `libandroid_runtime.so` を引き込むので Pie では厄介ですし、
そもそも**ワンセグの TS は平文の MPEG-2 TS**なので自前で扱えます。

### 3.3 CPRM も実装しない —— 録画は TS をそのまま書くだけ

**設計決定（2026年9月）**: 録画は**受信した TS をバイト単位でファイルに書くだけ**にし、
CPRM は実装しません。

これは何かを迂回しているわけではありません。

- **受信経路に暗号は無い。** ワンセグは平文で送出されています
  （[`06-調査ログ.md`](06-調査ログ.md) 第11節）。解くべきスクランブルが存在しません。
- **CPRM は Samsung が SD カードに書く録画に被せていたラッパ**で、
  `/efs/` から鍵を取っていました。自作アプリはその形式を**そもそも作りません**。
  平文 `.ts` を書くのは「CPRM を外す」ではなく「最初から付けない」です。

`libonesegcprmapi.so` のマーカーに `/efs/` があったのは、
**暗号が録画パスにあって受信パスには無い**ことの実装側の裏付けでした。
録画を自前でやると決めた時点で、**`/efs` への依存も消えます**
（IMEI のバックアップとしての `/efs` は当然別途必要です）。

これで移植対象から外れるもの:

```
libonesegcprmapi.so   libsdtvcrypto.so   libonesegdemux.so
libsdtvphmem.so       libBroadcastProcObs.so
bin/OneSegTsDemux     bin/broadcastProcessObserver
```

**残るのはティア 1 の 3 ファイルだけ**になりました。

視聴と録画が同じデータ経路の分岐になるので、録画機能の実装コストは
**ファイルを 1 つ開いて `write()` するだけ**です。詳細は
[`08-アプリ設計.md`](08-アプリ設計.md)。

なお、TS には放送のコピー制御信号（`digital_copy_control_descriptor`）が
乗っています。ARIB の受信機規定に準拠した製品なら従うべきものです。
自分の端末での私的な録画と、製品として配布する場合とでは話が別なので、
**配布を考えるならそこは見直す点**です。

### 3.4 ティア 3: サービス層とアプリ

| ファイル | 役割 |
|---|---|
| `lib/libSDtvService.so` | サービス本体（EPG マーカーあり） |
| `lib/libSDtvStack.so` | スタック |
| `lib/libbroadcastForOneSeg_jni.so` | **JNI 層。アプリから見た API** |
| `lib/libbroadcast_upgrade_jni.so` | アップデート |
| `lib/libOneSegfactorytest_jni.so` | 工場テスト |
| `app/MobileTV_JPN.apk` | **純正ワンセグアプリ** |

`MobileTV_JPN.apk` には `MobileTV_JPN.odex` が併存しています。
**4.0.4 の Dalvik boot classpath に対して最適化済み**ということで、
他のバージョンに持っていくには deodex が必須。
そして Android 9 は ART なので、**Dalvik の odex は結局使えません**。

### 3.5 ティア 4: データ放送 — **移植不要**

`libonesegdsmcc.so`, `libonesegbmlpeer.so`, `libsdsmcc.so`, `libonesegsp.so`,
`libBML.so`, `libBMLJNI.so`, `bin/OneSegDsmcc`

DSM-CC と BML は**データ放送**の実装です。そして
**データ放送は 2025〜2026年に各局で終了しました**
（[`01-結論と実現可能性.md`](01-結論と実現可能性.md) 第3節）。
**もう送出されていない信号のために移植する意味はありません。**

### 3.6 ティア 5: NexPlayer — **移植不可能**

`lib/libnexplayerservice.so` の `DT_NEEDED` に
**`libsurfaceflinger_client.so`** が入っています。
これは **Android 9 に存在しないライブラリ**です。
加えて `libandroid_runtime.so`、`libgui.so`、`libbinder.so` にも依存。

**移植は不可能で、かつ不要**です。H.264 + AAC は `MediaCodec` が普通に再生します。

### 3.7 紛らわしいが無関係なもの

- `lib/libMciAtscMh.so` — **ATSC-M/H**（米国のモバイル TV 規格）。
  文字列に ISDBT が含まれるだけで、ワンセグとは無関係。
- `bin/at_distributor` — AT コマンドのディスパッチャ。
  工場テスト用のコマンドで ISDBT に言及しているだけ。

## 4. 次にやること

### 4.1 `libonesegdmxdriver.so` の API を見る ★最優先

**これが分かれば、自前コードから直接チューナを叩けます。**

```bash
python3 tools/analyze-oneseg-blobs.py oneseg-report/ --symbols libonesegdmxdriver
```

探すのは 3 つです。

1. **オープン / 電源投入** の関数
2. **チャンネル or 周波数を指定する** 関数
3. **TS を読み出す** 関数

この 3 つが揃えば、ワンセグ移植の最小 API が確定します。

同時にこちらも見ておくと、上位からどう呼ばれているかが分かります。

```bash
python3 tools/analyze-oneseg-blobs.py oneseg-report/ --symbols libonesegutils
python3 tools/analyze-oneseg-blobs.py oneseg-report/ --symbols libbroadcastForOneSeg_jni
```

### 4.2 dmesg を取り直す

ワンセグアプリを起動して実際に視聴してから:

```bash
adb shell su -c 'dmesg' | grep -i isdbt
```

`isdbt_gpio_on` や `>ISDBT<` が見えれば、電源シーケンスが確認できます。

### 4.3 SPI 通信をキャプチャする（本命の一手）

`kernel/patches/0001-nmi326-add-optional-SPI-protocol-tracing.patch` を当てた
カーネルを **純正 4.0.4 上で** 動かし、純正アプリが NMI326 に流す
コマンド列をそのまま記録します。

API 名（4.1）とコマンド列（これ）が両方あれば、
**純正ライブラリ無しで再実装する道**が開けます。

### 4.4 バックアップ

まだなら今すぐ。

```bash
adb shell su -c 'dd if=/dev/block/platform/msm_sdcc.1/by-name/efs of=/sdcard/efs.img'
adb pull /sdcard/efs.img
```

## 6. 修正した箇所

この調査を受けて、リポジトリに以下を反映しました。

- `device/samsung/d2dcm/rootdir/etc/init.oneseg.rc` —
  `/dev/isdbt` を `media:media 0660` から **実機どおりの `system:system 0666`** へ
- `device/samsung/d2dcm/proprietary-files.txt` —
  空だったワンセグ節に、**実際のファイル名をティア分けして記載**
- `tools/analyze-oneseg-blobs.py` — `--symbols` を追加（エクスポート関数の一覧）
- `tools/oneseg-probe.sh` —
  `/system/etc` と `/system/bin` の取りこぼしを `/sdcard` 経由で再取得する
  フォールバックを追加。ファームウェア探索と apk 内 .so の展開も追加
