# 07. 実機調査の結果 — SC-06D 実機から判明したこと

**このドキュメントだけは実機の出力に基づいています。** 他のドキュメントは
公開ソースの読解が根拠ですが、ここは実際の SC-06D から取れた事実です。

- 端末: SC-06D / `d2dcm`
- ROM: **Android 4.0.4**、`samsung/d2om/d2dcm:4.0.4/IMM76D/SC06DOMAMA2:user/release-keys`
- 取得方法: `tools/oneseg-probe.sh` + `tools/analyze-oneseg-blobs.py`
- スキャンした ELF: **788 個**

---

## 1. 結論を先に

**ワンセグ移植の見通しは、事前の想定よりかなり良いです。**

理由は 1 つです。**`/dev/isdbt` を開いているライブラリが 1 つだけで、
しかもその依存関係が異常に軽い**ことが分かりました。

```
libonesegdmxdriver.so          ← /dev/isdbt を開くのはこれだけ
    ├── libonesegutils.so
    │       └── libPGL.so
    └── liblog / libcutils / libutils / libc / libstdc++ / libm  (AOSP)
```

**移植すべき独自ライブラリは 3 つだけ**です。そして重要なのは、
このチェーンが **`libbinder.so` も `libandroid_runtime.so` も
`libsurfaceflinger_client.so` も要求していない**ことです。

さらに、**録画を「TS をそのまま書く」方式にする**と決めたので
（3.3 節）、CPRM とその周辺も移植対象から外れました。
**純正から持ち込むのは、この 3 ファイルで全部です。**

この 3 つは Jelly Bean 時代の blob を Android 9 で動かすときに
最も詰まる相手で、特に `libsurfaceflinger_client.so` は
**Android 9 には存在すらしません**。それを避けて通れる、というのが今回の最大の収穫です。

## 2. カーネル側 — 想定通り動いている

```
OK   char major 225 registered: 225 isdbt
OK   /dev/isdbt: crw-rw-rw- system system 225, 0
```

`docs/06-調査ログ.md` でソースから読み取った内容（char major 225、
`register_chrdev` + `class_create` + `device_create`）が、実機で裏付けられました。

### パーミッションは `system:system 0666`

**当初この値を `media:media 0660` と想定していましたが、間違いでした。**
実機は **owner/group が `system`、モードが 0666**（誰でも読み書き可）です。

`device/samsung/d2dcm/rootdir/etc/init.oneseg.rc` を実機の値に修正済みです。
ここを締めると純正ライブラリが EACCES で転ぶので、**まず 0666 で動かしてから
締める**のが正しい順序です。

### dmesg は空振り

```
WARN no isdbt/nmi326 lines in dmesg
```

リングバッファが一周しただけです。**ワンセグアプリを起動してから再実行**すれば
`>ISDBT<` のログが取れます（`CONFIG_ISDBT_NMI_DEBUG=y` 相当が純正でも有効なら）。

## 2b. チューナは生きている（実機実行の結果）

`tools/isdbt-dump` を純正 4.0.4 の実機で実行した結果です。

```
opening /dev/isdbt ...  ok (fd 3)
ioctls:
  POWER_ON                 ok
  INTERRUPT_REGISTER       ok
  INTERRUPT_ENABLE         ok
  INTERRUPT_HANDLER_START  ok
```

dmesg 側:

```
>ISDBT< <isdbt> poll
>ISDBT< <isdbt> poll: release (0)
   ...
>ISDBT< ISDBT_POWER_OFF enter..
isdbt_gpio_off
>ISDBT< <isdbt> isdbt release
```

### 分かったこと

**1. ハードウェアは生きています。**
`/dev/isdbt` が開き、`POWER_ON` が通り、GPIO の電源シーケンスが走り、
`isdbt_gpio_off` まで正常に完了しました。14年前の端末ですが、
**チューナの電源経路は健在**です。これが確認できたのは大きい。

**2. `poll()` は永久にタイムアウトします（これは正常）。**

```
reads: 0   poll timeouts: 19   bytes read: 0
```

ドライバの `isdbt_poll()` は `g_bCatchIrq == 1` のときだけ `POLLIN` を返し、
`g_bCatchIrq` を立てるのは `isdbt_irq_handler()` だけです。そして割り込みは
**チューナが何か言うことがあるときにしか上がりません**。

チューニングしていない chip は何も言わないので、`poll` は返らない。
`poll: release (0)` が並ぶのは**そういう意味**で、故障ではありません。

→ `isdbt-dump` に `-n`（poll を飛ばして直接読む）を追加しました。
既定でも 3 回タイムアウトしたら 1 回だけ盲目読み出しを試します。

**3. カーネル警告が出ました。ドライバ側のバグです。**

```
WARNING: at kernel/irq/manage.c:1183 __free_irq+0x88/0x1b8()
Trying to free already-free IRQ 350
  isdbt_ioctl+0x1e4/0x2fc
```

**害はありません**（WARN であってクラッシュではなく、その後 POWER_OFF まで正常）。
ただし原因は本物のバグです。

`isdbt_release()` を見ると:

```c
static int isdbt_release(struct inode *inode, struct file *filp)
{
	...
	pdev->irq_status = DTV_IRQ_DEINIT;
	g_bCatchIrq = 0;
	kfree(pdev->rwBuf);
	kfree((void *)pdev);      /* ← free_irq() を呼んでいない */
	return 0;
}
```

`request_irq()` は `pdev` を `dev_id` として登録します。
`UNREGISTER` せずにプロセスが終了すると、**IRQ は kfree 済みメモリを指したまま
登録され続けます**。次の割り込みで解放済みの `pdev` に対してハンドラが走る、
という use-after-free です。

そして次に開いたプロセスは新しい `pdev` を持つので、その `UNREGISTER` の
`free_irq(irq, new_pdev)` は登録済みアクションの `dev_id` と一致せず、
カーネルが「already-free」と警告する —— これが今回見えた症状です。

**修正パッチを用意しました**: `kernel/patches/0002-nmi326-free-the-IRQ-on-release.patch`
（lineage-16.0 と CM13 の両カーネルに適用可能なことを確認済み）。
LineageOS 側のカーネルは自分でビルドするので、**この穴は塞いだ状態で出せます**。

なお純正 ROM 側では直せないので、警告が出ても気にしないでください。
気になる場合は再起動すれば IRQ の状態はクリアされます。

## 3. ユーザー空間 — スタックの全体像

Samsung / NTT 系の「SDtv」スタックでした。

### 3.1 ティア 1: チューナに触る最小構成 ★

| ファイル | 役割 |
|---|---|
| `lib/libonesegdmxdriver.so` | **`/dev/isdbt` を開く唯一のライブラリ** |
| `lib/libonesegutils.so` | 共通ユーティリティ |
| `lib/libPGL.so` | その下請け |

`libonesegdmxdriver.so` の `DT_NEEDED`:

```
libonesegutils.so, liblog.so, libcutils.so, libutils.so,
libc.so, libstdc++.so, libm.so
```

AOSP 側で気にすべきは実質 **`libutils.so` だけ**です（C++ ABI が JB と Pie で違う）。
`liblog` / `libcutils` は C API で比較的安定、`libc` / `libm` は問題なし。
`libstdc++.so` は Android 9 にも存在するはずですが、**要確認**です。

`libutils.so` で詰まった場合の対処は、d2att-unified がすでに持っている
`libsamsung_symbols`（互換シンボル層）を拡張することです。

### 3.2 ティア 2: 純正の TS デマルチプレクサ — **不要と決定**

| ファイル | 役割 |
|---|---|
| `lib/libonesegdemux.so` | TS 分離 |
| `lib/libsdtvphmem.so` | 共有メモリ |
| `lib/libsdtvcrypto.so` | 暗号処理 |
| `lib/libonesegcprmapi.so` | CPRM（録画保護）。`/efs/` を読む |
| `lib/libBroadcastProcObs.so` | プロセス監視 |
| `bin/OneSegTsDemux` / `bin/broadcastProcessObserver` | デーモン |

**このティアは丸ごと移植しません。** `libonesegdemux.so` は
`libbinder.so` と `libandroid_runtime.so` を引き込むので Pie では厄介ですし、
そもそも**ワンセグの TS は平文の MPEG-2 TS**なので自前で扱えます。

### 3.3 CPRM も実装しない —— 録画は TS をそのまま書くだけ

**設計決定（2026年9月）**: 録画は**受信した TS をバイト単位でファイルに書くだけ**にし、
CPRM は実装しません。

これは何かを迂回しているわけではありません。

- **受信経路に暗号は無い。** ワンセグは平文で送出されています
  （[`06-調査ログ.md`](06-調査ログ.md) 第11節）。解くべきスクランブルが存在しません。
- **CPRM は Samsung が SD カードに書く録画に被せていたラッパ**で、
  `/efs/` から鍵を取っていました。自作アプリはその形式を**そもそも作りません**。
  平文 `.ts` を書くのは「CPRM を外す」ではなく「最初から付けない」です。

`libonesegcprmapi.so` のマーカーに `/efs/` があったのは、
**暗号が録画パスにあって受信パスには無い**ことの実装側の裏付けでした。
録画を自前でやると決めた時点で、**`/efs` への依存も消えます**
（IMEI のバックアップとしての `/efs` は当然別途必要です）。

これで移植対象から外れるもの:

```
libonesegcprmapi.so   libsdtvcrypto.so   libonesegdemux.so
libsdtvphmem.so       libBroadcastProcObs.so
bin/OneSegTsDemux     bin/broadcastProcessObserver
```

**残るのはティア 1 の 3 ファイルだけ**になりました。

視聴と録画が同じデータ経路の分岐になるので、録画機能の実装コストは
**ファイルを 1 つ開いて `write()` するだけ**です。詳細は
[`08-アプリ設計.md`](08-アプリ設計.md)。

なお、TS には放送のコピー制御信号（`digital_copy_control_descriptor`）が
乗っています。ARIB の受信機規定に準拠した製品なら従うべきものです。
自分の端末での私的な録画と、製品として配布する場合とでは話が別なので、
**配布を考えるならそこは見直す点**です。

### 3.4 ティア 3: サービス層とアプリ

| ファイル | 役割 |
|---|---|
| `lib/libSDtvService.so` | サービス本体（EPG マーカーあり） |
| `lib/libSDtvStack.so` | スタック |
| `lib/libbroadcastForOneSeg_jni.so` | **JNI 層。アプリから見た API** |
| `lib/libbroadcast_upgrade_jni.so` | アップデート |
| `lib/libOneSegfactorytest_jni.so` | 工場テスト |
| `app/MobileTV_JPN.apk` | **純正ワンセグアプリ** |

`MobileTV_JPN.apk` には `MobileTV_JPN.odex` が併存しています。
**4.0.4 の Dalvik boot classpath に対して最適化済み**ということで、
他のバージョンに持っていくには deodex が必須。
そして Android 9 は ART なので、**Dalvik の odex は結局使えません**。

### 3.5 ティア 4: データ放送 — **移植不要**

`libonesegdsmcc.so`, `libonesegbmlpeer.so`, `libsdsmcc.so`, `libonesegsp.so`,
`libBML.so`, `libBMLJNI.so`, `bin/OneSegDsmcc`

DSM-CC と BML は**データ放送**の実装です。そして
**データ放送は 2025〜2026年に各局で終了しました**
（[`01-結論と実現可能性.md`](01-結論と実現可能性.md) 第3節）。
**もう送出されていない信号のために移植する意味はありません。**

### 3.6 ティア 5: NexPlayer — **移植不可能**

`lib/libnexplayerservice.so` の `DT_NEEDED` に
**`libsurfaceflinger_client.so`** が入っています。
これは **Android 9 に存在しないライブラリ**です。
加えて `libandroid_runtime.so`、`libgui.so`、`libbinder.so` にも依存。

**移植は不可能で、かつ不要**です。H.264 + AAC は `MediaCodec` が普通に再生します。

### 3.7 紛らわしいが無関係なもの

- `lib/libMciAtscMh.so` — **ATSC-M/H**（米国のモバイル TV 規格）。
  文字列に ISDBT が含まれるだけで、ワンセグとは無関係。
- `bin/at_distributor` — AT コマンドのディスパッチャ。
  工場テスト用のコマンドで ISDBT に言及しているだけ。

## 4. チューナ API が判明した ★

`libonesegdmxdriver.so` は **141 個のシンボルを C リンケージで公開**しています。
C++ のマングリングが無いので、**`dlopen` + `dlsym` でそのまま呼べます**。

### 4.1 高レベル API — これが本体

```c
OneSegDrv_Initailze          /* 初期化（Samsung の綴り間違いそのまま） */
OneSegDrv_Finalize
OneSegDrv_SetChannel         /* ★ チューニング */
OneSegDrv_ReleaseChannel
OneSegDrv_ReadData           /* ★ TS 読み出し */
OneSegDrv_CheckChannelLock   /* ロックしたか */
OneSegDrv_CheckChipState
OneSegDrv_CheckSWFrameLock
OneSegDrv_GetRSSI            /* 受信強度 */
OneSegDrv_GetCN              /* C/N 比 */
OneSegDrv_GetBerPer          /* BER / PER */
OneSegDrv_GetADC
OneSegDrv_GetSFN
OneSegDrv_GetSingalStatistics  /* これも綴り間違い（Singal） */
```

**探していた 3 つがそのまま揃っています。** 初期化・チャンネル指定・TS 読み出し。
おまけに受信品質の取得まで公開されています。

### 4.2 中間層

```c
oneseg_drv_open / oneseg_drv_close
oneseg_init / oneseg_probe
oneseg_power_on / oneseg_power_off
oneseg_set_channel / oneseg_start_channel / oneseg_release_channel
oneseg_lock_check / oneseg_sw_frame_lock_check
oneseg_rssi_measure / oneseg_cn_measure / oneseg_ber_per_measure
oneseg_isr
```

### 4.3 低レベル — NMI326 のレジスタ直叩き

```c
BBM_INIT / BBM_DEINIT / BBM_PROBE / BBM_RESET
BBM_POWER_ON / BBM_POWER_OFF
BBM_READ / BBM_WRITE / BBM_BYTE_READ / BBM_WORD_READ / BBM_LONG_READ / BBM_BULK_READ
BBM_TUNER_SELECT / BBM_TUNER_DESELECT / BBM_TUNER_READ / BBM_TUNER_WRITE
BBM_TUNER_SET_FREQ           /* 周波数を直接指定できる */
```

BBM = BaseBand Modem。**レジスタレベルまで露出しています。**
高レベル API が期待どおりに動かなくても、ここから組み立て直せます。

### 4.4 OEM 層 — `/dev/isdbt` を触っているのはここ

```c
oem_init_spi / oem_deinit_spi
oem_bus_read / oem_bus_write
oem_power_on / oem_power_off
oem_rst_up_dtv / oem_rst_dn_dtv
oem_interrupt_init / _enable / _disable / _done / _deinit
```

**カーネルの ioctl 名と 1 対 1 で対応しています**
（`oem_interrupt_done` ↔ `IOCTL_ISDBT_INTERRUPT_DONE` など）。
このライブラリのどこで `/dev/isdbt` を開いているかが、これで説明できます。

### 4.5 注目すべきグローバル変数

```c
ghTsDataFileDescr    /* おそらく /dev/isdbt の fd */
g_pfdtvtscb          /* ★ TS のコールバック関数ポインタ */
g_ShareQue           /* 共有キュー */
gIsdbtSqInfo         /* 受信品質の構造体 */
error_description / error_info / get_last_err_info()   /* エラー文字列 */
___Date / ___Revision / ___URL / _get_revision_info()  /* ビルド情報 */
```

**`g_pfdtvtscb` は重要です。** TS が `OneSegDrv_ReadData` の戻り値ではなく
**コールバック経由で来る**可能性を示しています。`ReadData` が 0 を返し続けたら、
こちらを疑ってください。

### 4.6 気に留めておく点

- **`i2s_snd`** というシンボルがあります。NMI326 は音声を **I2S で別出力**できる
  チップなので、`ReadData` から出てくる TS が**映像のみ**の可能性があります。
  最初のキャプチャを `ffprobe` にかけて、音声ストリームの有無を確認してください。
- `atvtestpattern` / `nmi_atv_set_chroma_gain` — このチップは**アナログ TV** にも
  対応しています（日本では無関係）。
- 綴り間違い（`Initailze`、`Singal`）は**そのまま使ってください**。直すと解決しません。

### 4.7 呼び出し方 — `tools/oneseg-api-probe.c`

シンボル名は分かりましたが、**引数の型は分かりません**（C リンケージなので
シンボルに型情報が入っていない）。それを実機で調べるためのハーネスを用意しました。

ARM の呼び出し規約では整数引数の先頭 4 個が r0〜r3 に入り、呼び出し側が後始末を
するので、**必要より多い引数で呼ぶのは安全**です（余ったレジスタは無視される）。
逆に少ないと呼ばれた側がゴミを読みます。なので全部 4 引数で呼びます。

外れた場合に備えて、各呼び出しは SIGSEGV / SIGBUS / SIGILL ハンドラの下で実行し、
`siglongjmp` で戻ります。**1 回の誤りで全体が死にません。**

```bash
# 1. 安全: ロードとシンボル解決とビルド情報だけ。チューナには触らない
adb shell su -c '/data/local/tmp/oneseg-api-probe'

# 2. 実際にチューニング（物理チャンネル 27、10 秒）
adb shell su -c '/data/local/tmp/oneseg-api-probe -t 27 -s 10 -o /sdcard/ch27.ts'
```

**これは純正 ROM のまま実行できます。** LineageOS を焼く前に、
チューニング手順とハードの生死を確定できる、ということです。

## 5. 次にやること

### 5.1 まず配線確認（NDK 不要）

```bash
sudo apt install gcc-arm-linux-gnueabihf
arm-linux-gnueabihf-gcc -static -O2 -o isdbt-dump tools/isdbt-dump.c
adb push isdbt-dump /data/local/tmp/ && adb shell chmod 755 /data/local/tmp/isdbt-dump
adb shell su -c '/data/local/tmp/isdbt-dump -s 10'
adb shell su -c 'dmesg | tail -40'      # isdbt_gpio_on が出れば電源が入った
```

### 5.1b PIE の罠 — Android 4.0.x では PIE バイナリが動かない

**これで一度詰まりました。** 記録しておきます。

NDK r21e で API 16 を狙ってビルドすると **PIE（位置独立実行形式）** になります。
ところが **Android の linker が PIE を読めるようになったのは 4.1（API 16）から**で、
この端末は **4.0.4 = API 15**。PIE バイナリは `main()` に入る前に落ちます。

```
$ file oneseg-api-probe
... ELF 32-bit LSB shared object, ARM ...      ← これが PIE
$ adb shell su -c '/data/local/tmp/oneseg-api-probe'
Segmentation fault
```

**出力が 1 行も出ないのが特徴**です（起動前に死ぬので）。

対処は 2 つ:

```bash
# 1. 非PIE でビルドする
clang -fno-pie -no-pie -O2 -o oneseg-api-probe tools/oneseg-api-probe.c -ldl

# 2. 確認する。ET_EXEC(2) なら OK、ET_DYN(3) なら PIE
od -An -tu1 -j16 -N1 oneseg-api-probe      #  2 が出れば正しい
```

`file` の表記は版によって違います（`shared object` と書く版と
`pie executable` と書く版がある）ので、**ELF ヘッダの `e_type` を直接見るのが確実**です。

`isdbt-dump` が動いたのは `-static` で作ったからで、静的リンクは既定で非PIE になります。

### 5.1d もう一つの罠 — GNU hash

PIE を切っても、なお `main()` の 1 行目に届かず落ちることがあります。
バッファなし出力にしても**何も出ない**なら、ローダ段階で死んでいます。

原因はシンボルテーブルのハッシュ形式です。

- 現代のリンカ（lld を含む）は既定で **`.gnu.hash` だけ**を出力します
- **Android の linker が `.gnu.hash` を読めるようになったのは 6.0（API 23）から**
- それ以前は **`DT_HASH` しか見ません**

`DT_HASH` の無いバイナリを 4.x の linker に渡すと、`nbucket` が 0 のまま
`hash % nbucket` を計算し（ARM の除算はトラップせず 0 を返す）、
未初期化のバケット配列を読みに行って **SIGSEGV** します。
**ロード中なので、当然何も出力されません。**

確認:

```bash
readelf -d oneseg-api-probe | grep -i hash
```

| 出力 | 判定 |
|---|---|
| `(GNU_HASH)` のみ | **NG**。4.x では起動しない |
| `(HASH)` がある | OK |

対処:

```bash
clang -fno-pie -no-pie -Wl,--hash-style=sysv -O2 -o oneseg-api-probe ... -ldl
```

`build-android.sh` はこのフラグを付けてビルドし、**結果のハッシュ形式も検査**します。

### 5.1e 起動しない原因を実機から知る方法

Android の linker はエラーを logcat に出します。推測する前にこれを見てください。

```bash
adb logcat -c
adb shell su -c '/data/local/tmp/oneseg-api-probe'
adb logcat -d | grep -iE 'linker|oneseg|cannot|DEBUG|SIGSEGV|library'
```

`CANNOT LINK EXECUTABLE` や `cannot locate symbol "..."` が出れば原因が確定します。
何も出ずに segfault だけなら、上の GNU hash かそれに類するローダ側の非互換です。

### 5.1c ビルドスクリプトを使うほうが早い

フラグを覚えなくて済むように用意しました。

```bash
./tools/build-android.sh
```

両方のツールを正しいフラグでビルドし、**PIE になっていないかを `e_type` で検査**して、
push 用のコマンドまで出します。足りないツールチェインがあれば入れ方を教えます。

### 5.2 API を叩く（NDK が要る）

`oneseg-api-probe` は Bionic のライブラリを `dlopen` するので、
自身も Bionic の動的リンクバイナリである必要があります。ここだけは NDK が要ります。

Debian/Ubuntu に使える NDK のパッケージは無いので直接落とします。
アカウント登録も SDK Manager も不要、約 1GB です。

```bash
cd ~
wget https://dl.google.com/android/repository/android-ndk-r21e-linux-x86_64.zip
unzip -q android-ndk-r21e-linux-x86_64.zip
export ANDROID_NDK="$HOME/android-ndk-r21e"
```

そのままリポジトリのルートで:

```bash
cd ~/lineage-sc-06
"$ANDROID_NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/armv7a-linux-androideabi16-clang" \
    -O2 -o oneseg-api-probe tools/oneseg-api-probe.c -ldl

file oneseg-api-probe    # "ELF 32-bit LSB ... ARM ... dynamically linked" ならOK
```

**r21e である必要があります。** API 16 を狙える最後の系列で、この端末は API 15 です。
新しい NDK は API 21 からなので、作ったバイナリが起動しません。

**アンテナを伸ばしてから**実行してください。

### 5.3 取れた TS を PC で確認

```bash
adb pull /sdcard/ch27.ts && ffprobe ch27.ts
```

**`ffprobe` がストリームを認識したら、実質ゴールです。**

### ファームウェアについての補足

`/system/etc/firmware/` を全部見た結果、あったのは

```
a225_pfp.fw, a225_pm4.fw, a225p5_pm4.fw, a300_pfp.fw, a300_pm4.fw   ← Adreno GPU
leia_pfp_470.fw, leia_pm4_470.fw                                    ← 同上
vidc_1080p.fw                                                       ← ビデオコーデック
cyttsp_8960_cdp.hex                                                 ← タッチパネル
```

**ワンセグ用のファームウェアはありません。** `/system/etc/one-seg/` にあるのは
BML（データ放送）のフォント・音・DB だけで、チューナのファームではありません。

つまり NMI326 のファームウェアは **`libonesegdmxdriver.so` の中に配列として
埋め込まれている**可能性が高い、ということです。移植の観点ではむしろ好都合で、
**別途持ち出すファイルが 1 つ減ります**。
