# 05. ワンセグ移植の手順

Android 9 (LineageOS 16.0) の SC-06D でワンセグを動かすための、段階的な攻略手順です。

**成功は保証できません。** ただしこの順序で進めれば、**どこで詰まるかは必ず特定できます**。
そして詰まる場所によって、その先に望みがあるかどうかが判断できます。
中途半端な「動きませんでした」で終わらせないための手順です。

各ステップに **判定** を書いてあります。判定が NG なら、そのステップの
「NG のときどうするか」に従ってください。

---

## 全体像

```
  ステップ 0  純正から情報を吸い出す      ← LineageOS を焼く前に必須
  ステップ 1  LineageOS 16.0 を起動させる
  ステップ 2  /dev/isdbt が出ることを確認  ← カーネル側のゴール
  ステップ 3  チューナが生きていることを確認（電源 ON の ioctl）
  ステップ 4  純正ライブラリの依存関係を調べる  ← 最初の関門
  ステップ 5  純正スタックを載せて読み込ませる
  ステップ 6  TS が取れるところまで持っていく  ← ここが実質のゴール
  ステップ 7  TS を再生する
```

ステップ 4 で詰まったら 5 以降には進めません。

**ステップ 6 まで行けば、事実上勝ちです。** ワンセグ放送はスクランブルされておらず、
取り出した TS は平文の MPEG-2 TS（H.264 + AAC）なので、再生は普通の処理です。
（初版ではここに「RMP 復号」という最大の関門があると書いていましたが、
調べ直した結果それは誤りでした。[`06-調査ログ.md`](06-調査ログ.md) 第11節）

---

## ステップ 0 — 純正から情報を吸い出す

**LineageOS を焼く前に、純正 + root の状態で実行してください。**
4.0.4 でも 4.1.2 でも構いません。ワンセグは発売時（4.0.4）から搭載されています。
焼いた後では二度と取れません。

```bash
./tools/oneseg-probe.sh
./tools/analyze-oneseg-blobs.py oneseg-report/
```

得られるもの:

| ファイル | 何がわかるか |
|---|---|
| `dmesg-isdbt.txt` | 純正カーネルでドライバが正常に probe しているか |
| `dev-isdbt.txt` | `/dev/isdbt` の**正しい owner/group/mode** |
| `hits-devnode.txt` | **`/dev/isdbt` を開いているライブラリはどれか** |
| `hits-rmp.txt` | 録画 DRM のコードの所在（視聴には不要だが、層の切り分けに有用） |
| `by-name.txt` | 実際のパーティション構成（`BoardConfig.mk` 用） |
| `ueventd.txt` | 純正の ueventd ルール |
| `proprietary-files.oneseg.txt` | blob 候補リスト |

**判定**: `hits-devnode.txt` に 1 件以上あること。

**NG のときどうするか**: 何も引っかからないなら、
`/system/lib` が pull できていないか（`probe.log` を確認）、
ワンセグの実装が apk の中の `lib/armeabi/` にある可能性があります。
候補 apk を `unzip` して中の `.so` を調べてください。

## ステップ 1 — LineageOS 16.0 を起動させる

[`03-ビルド手順.md`](03-ビルド手順.md) と [`04-書き込み手順.md`](04-書き込み手順.md) の通り。

**この段階ではワンセグ関連を一切入れないでください。** 素の状態で起動することを
先に確定させないと、後で何が原因か切り分けられなくなります。

**判定**: 起動して、通話と Wi-Fi が動くこと。

---

## ステップ 2 — `/dev/isdbt` を確認する

```bash
adb shell ls -l /dev/isdbt
adb shell 'cat /proc/devices | grep 225'
adb shell 'dmesg | grep -i isdbt'
```

期待する結果:

```
crw-rw---- 1 root root 225, 0 ... /dev/isdbt
225 isdbt
<isdbt> isdbt_init
<isdbt> isdbt_probe, MAJOR = 225
```

**判定**: `/dev/isdbt` が存在し、`isdbt_probe` が成功していること。

**なぜ出るはずなのか**: `lineageos_d2dcm_defconfig` に `CONFIG_ISDBT_NMI=y` が入っており、
ドライバは `class_create()` と `device_create()` を呼ぶので ueventd がノードを作ります。

**NG のときどうするか**:

- `/proc/devices` に 225 が無い → カーネルにドライバが入っていない。
  ビルドしたカーネルの `.config` を確認（[`03-ビルド手順.md`](03-ビルド手順.md) 第5節）。
- 225 はあるが `/dev/isdbt` が無い → ueventd がノードを作っていない。
  `device/samsung/d2dcm/rootdir/etc/init.oneseg.rc` を ramdisk から import するか、
  ueventd ルールを足してください。
- `isdbt_probe` が出ない → `CONFIG_MACH_M2_DCM` が有効でない可能性。
  `board-m2_dcm.c` の `isdbt_dev_init()` が呼ばれていません。

**ここまで到達すれば、カーネル側は完了です。** 以降はすべてユーザー空間の話になります。

## ステップ 3 — チューナが生きているか確認する

`/dev/isdbt` を開いて `IOCTL_ISDBT_POWER_ON` を投げます。ハードウェアが応答するかの確認です。

**[`tools/isdbt-dump.c`](../tools/isdbt-dump.c) を用意してあります。**
open → `POWER_ON` → 割り込み登録 → `poll()`/`read()` → ファイル保存まで一通りやり、
読めたものが MPEG-2 TS かどうかも判定します。

**NDK は不要です。** このプログラムは POSIX しか使わないので、
Ubuntu のクロスコンパイラで静的リンクすれば Android で動きます。

```bash
sudo apt install gcc-arm-linux-gnueabihf
arm-linux-gnueabihf-gcc -static -O2 -o isdbt-dump tools/isdbt-dump.c

adb push isdbt-dump /data/local/tmp/
adb shell chmod 755 /data/local/tmp/isdbt-dump
adb shell su -c '/data/local/tmp/isdbt-dump -s 10 -o /sdcard/isdbt.bin'
adb shell su -c 'dmesg | tail -40'
```

動かない場合は soft-float 版を試してください
（`gcc-arm-linux-gnueabi` / `arm-linux-gnueabi-gcc`）。

**`-static` が重要です。** 動的リンクだと Android 4.0.4 のローダでは起動しません。

実行後に `dmesg` を見ます。

```bash
adb shell 'dmesg | grep -i isdbt | tail -20'
```

期待するログ（`board-m2_dcm.c` の `isdbt_gpio_on()` が出すもの）:

```
isdbt_gpio_on
```

**判定**: `isdbt_gpio_on` がログに出て、エラーが出ないこと。

**これが通れば、チューナの電源は入っています。** ハードは生きています。
14年前の端末なので、ここで初めて「物理的に壊れていない」ことが確認できます。

**NG のときどうするか**:

- `open` が `EACCES` → パーミッション。ステップ 2 の init.oneseg.rc を見直す。
  SELinux が enforcing なら permissive にして切り分ける。
- `POWER_ON` が失敗 → GPIO の要求に失敗している。`dmesg` に
  `Failed to request gpio` が出ていないか確認。

## ステップ 4 — 純正ライブラリの依存関係を調べる ★最初の関門

> **実機で調査済みです。** SC-06D（4.0.4）での結果は
> [`07-実機調査の結果.md`](07-実機調査の結果.md) にあります。
> 結論は **パターン B 寄りの好条件**: `/dev/isdbt` を開く
> `libonesegdmxdriver.so` の依存は `libonesegutils.so` → `libPGL.so` と
> AOSP の基本ライブラリだけで、`libbinder` / `libandroid_runtime` /
> `libsurfaceflinger_client` を含みません。
> 以下は、その結果をどう読むかの一般論として残してあります。

ステップ 0 で特定した「`/dev/isdbt` を開いているライブラリ」が、
Android 9 で読み込めるかを判断します。

```bash
./tools/analyze-oneseg-blobs.py oneseg-report/
```

出力の `[MISSING]` の行を見てください。ここに何が並ぶかで難易度が決まります。

### パターン A: `[MISSING]` が無い、または自前のライブラリだけ

**最も望みがあります。** スタックが自己完結しています。ステップ 5 へ。

### パターン B: `libc.so` / `liblog.so` / `libdl.so` だけ

**望みがあります。** これらは Android 9 にもあり、ABI もおおむね保たれています。ステップ 5 へ。

### パターン C: `libutils.so` / `libbinder.so` / `libcutils.so` / `libmedia.so` を含む

**厳しくなります。** これらは Jelly Bean と Pie で ABI が変わっています。
特に `libbinder` は C++ の内部構造ごと変わっているので、そのままでは動きません。

対処:
1. **純正の .so を一緒に持ち込む** — `/system/lib/oneseg/` などに隔離して置く
2. **shim を書く** — `hardware/samsung/libsamsung_symbols` を拡張する
   （d2att-unified がすでにこの手法を使っています）
3. リンカ名前空間の設定（`/system/etc/ld.config.txt`）で隔離パスを許可する

### パターン D: `libstlport.so` を含む

manifest の `external/stlport` で対応できます。それ用に入れてあります。

**判定**: パターン A/B なら次へ。C/D なら shim の作業が入りますが、まだ進めます。

## ステップ 5 — 純正スタックを載せる

まず**最小構成**で試します。全部いっぺんに入れると切り分けられなくなります。

```bash
# 1. チューナ制御の .so だけを置いて、dlopen できるか確かめる
adb push libXXX.so /data/local/tmp/
adb shell 'LD_LIBRARY_PATH=/data/local/tmp /data/local/tmp/dlopen-test libXXX.so'
```

`dlopen` のエラーメッセージが最も情報量があります。

| エラー | 意味 | 対処 |
|---|---|---|
| `cannot locate symbol "X"` | ABI 不一致 | その関数を shim で提供する |
| `library "Y" not found` | 依存不足 | Y も持ち込む |
| `is not accessible for the namespace` | リンカ名前空間 | `ld.config.txt` を調整 |
| `has text relocations` | 古い .so | Android 9 は原則拒否。`allow_text_relocations` が要る |

`has text relocations` は要注意です。**Android 9 は text relocation を持つ .so の
ロードを既定で拒否します**。Jelly Bean 時代の .so では珍しくありません。

**判定**: 対象の .so が `dlopen` できること。

**NG のときどうするか**: ここで越えられない場合、**純正スタックの移植は断念**して、
ステップ 6 の「自作」ルートに切り替える判断になります。

---

## ステップ 6 — TS を取る

ここから 2 つのルートに分かれます。

### ルート 1: 純正スタックを使う（ステップ 5 が通った場合）

純正のワンセグ apk を入れて起動を試みます。ここでも壁があります。

- `targetSdkVersion` が低すぎて起動を拒否される → apk を書き換えて再署名
- 実行時パーミッションが下りない → `/system/etc/permissions/` の xml も一緒に入れる
- 非 SDK インターフェース制限 → `settings put global hidden_api_policy 1` で緩和して切り分け

### ルート 2: 自作する（ステップ 5 が通らなかった場合）

`/dev/isdbt` を直接叩くコードを書きます。**ここが本当に難しいところです。**

必要な情報:

- NMI326 のレジスタマップ
- ファームウェアのロード手順
- チューニングのコマンド列

これらは公開されていません。取得する方法は 2 つです。

1. **純正の .so を逆アセンブルする** — `/dev/isdbt` への `write()` の呼び出し元を追う
2. **純正 ROM 上で SPI の通信をキャプチャする** — カーネルドライバに
   ログを仕込んだカスタムカーネルを純正 ROM で動かし、
   ワンセグアプリが実際に流すバイト列を記録する

**2 が本命です。** ドライバは GPL でソースがあるので、
`nmi326_spi_drv.c` の read/write にログを足すだけで、
アプリが送るコマンド列がそのまま取れます。**これは合法かつ最も情報量の多い方法です。**

```c
/* nmi326_spi_drv.c の転送関数に足す */
print_hex_dump(KERN_DEBUG, ">ISDBT-TX< ", DUMP_PREFIX_OFFSET,
               16, 1, tx_buf, len, false);
```

**判定**: TS パケット（0x47 で始まる 188 バイト単位）が取れること。

## ステップ 7 — TS を再生する

**ここは難所ではありません。**

ワンセグ放送は**スクランブルされていません**。視聴に B-CAS カードも RMP 鍵も不要です
（根拠は [`06-調査ログ.md`](06-調査ログ.md) 第11節）。
ステップ 6 で取り出した TS は、そのまま中身が読める MPEG-2 TS です。

| 項目 | 内容 |
|---|---|
| コンテナ | MPEG-2 TS（188バイト固定長パケット、同期バイト 0x47） |
| 映像 | H.264 / AVC、320×180 前後、15fps |
| 音声 | AAC-LC（HE-AAC）、モノラルまたはステレオ |
| ビットレート | 全体で 400kbps 程度 |

### まず PC で確認する

一番確実な切り分けです。端末で再生を作り込む前に、TS が正しいことを確認します。

```bash
# 端末でファイルに落として
adb pull /sdcard/capture.ts

# PC で中身を見る
ffprobe capture.ts
ffplay capture.ts
```

`ffprobe` がストリームを認識すれば、**ワンセグの移植は成功しています**。
あとは再生を端末上でどう出すかだけの話になります。

同期バイトの確認だけなら:

```bash
xxd capture.ts | head -3     # 各188バイトの先頭が 47 になっていること
```

### 端末で再生する

選択肢が複数あります。どれでも構いません。

1. **`MediaCodec` / `MediaExtractor` で自作アプリ** — 一番素直。
   `/dev/isdbt` から TS を読んで、そのまま食わせる
2. **VLC for Android などに投げる** — TS ファイル / パイプを再生させる
3. **ローカルで HTTP か UDP に流す** — 既存プレイヤーがそのまま使える
4. **録るだけ** — ライブ視聴を諦めて、TS を保存して後で PC で見る

**3 が一番早く形になります。** チューナから読んだ TS を localhost に流すだけの
小さなプログラムを書けば、再生側は既存のプレイヤーで済みます。

### 字幕・番組表について

字幕（ARIB STD-B24）と EPG は TS の中に入っていますが、**日本独自の文字符号化**なので
一般的なプレイヤーはそのままでは表示できません。

- 字幕: `arib-b24`/`aribb24` 系のライブラリを使う
- EPG: TS の EIT を自分で解析する

**どちらも「映る」ようになった後の話**です。最初は無視して構いません。

### 録画について

録画データには受信機メーカー独自の DRM が付くのが本来の仕様ですが、
**それは純正アプリがやっていたこと**です。自分で TS を保存するぶんには関係ありません。

---

## 詰まったときに残るもの

仮にステップ 4〜6 のどこかで止まっても、**そこまでの成果は無駄になりません**。

- Android 9 が動く SC-06D が手に入っている
- ワンセグのハードが生きていることが確認できている
- どこが壁なのかが**具体的に特定できている**（「なんとなく動かない」ではない）
- SPI の通信ログという、他の誰も持っていない一次資料が残る

最後の 1 つは特に価値があります。SC-06D に限らず、
**NMI326 を積んだ他の日本向け Android 端末**にも通用する情報だからです。
